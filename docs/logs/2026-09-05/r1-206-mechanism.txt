=== Step 5: static-mechanism read (metadata source, per-decode or shared?) ===

The failing check at raw_contract_validate.cpp:346 reads input->black
(RawBlackPattern, per-call struct) and input->white_level[4] (per-call
struct), both populated once per decode by
libraw_gpu_input_adapter.cpp:450-478 from a local LibRaw "v" view of THAT
decode's own libraw_data_t (v.black_scalar, v.black_channel,
v.black_pattern, v.white_level -- all fields read off the per-call LibRaw
instance, not any static/global). No static or thread-shared mutable
state is visible in raw_contract_validate.cpp itself (pure function over
its RawGpuInput* argument) or in the black/white population path in
libraw_gpu_input_adapter.cpp. This is consistent with the campaign's
already-refuted "LibRaw instance sharing" route (plan §3): each decode
gets its own LibRaw instance and its own extracted v.black_scalar/
v.white_level, so a torn read between two concurrent decodes' metadata
would require them to be reading from the SAME LibRaw instance, which the
existing per-decode ownership model rules out by construction. I did not
find a plausible shared-state site that would produce this specific
failure under concurrency from a static read of these two files alone;
confirming it fully would require tracing LibRaw's own internal state
(third_party/libraw) for anything process-global (e.g. lazily-initialised
static tables consulted by unpacked_load_raw()/white balance defaults),
which is out of this ticket's scope (LibRaw internals, not ceyx code) and
I did not do it.

=== VERDICT ===

INCONCLUSIVE -- but not for the reason the ticket anticipated ("cannot
tell from static reading"). The premise itself does not hold: I cannot
reproduce ANY -206 failure, deterministic or otherwise, on
image_samples/raw_sample.arw (sha256-verified to be the exact file in
question) with the current tree. 3/3 runs succeeded with byte-identical
output, matching the file's own long-standing manifest expectation
(expect_error=kRawSuccess, P17 T6) and every other test fixture's
treatment of it as a known-good Bayer sample.

I therefore cannot compare "the deterministic failure's mechanism" against
the intermittent concurrent failure's mechanism, because there is no
currently-reproducible deterministic failure on this file to compare
against. Two possibilities, not adjudicated here (read-only scope):
  (a) the plan's risk #10 / ruling 3's "-206, quarantined" characterization
      of this file was incorrect from the start (possibly conflating it
      with a different, absent sample -- e.g. raw_corpus_manifest.json's
      other entries with sha256:"" that are not actually present on disk,
      such as image_samples/raw_corpus/sony_a7r4.arw), or
  (b) something upstream of this investigation's reach (build
      configuration, LibRaw version, a fix landed but not connected back
      to the plan doc) resolved it, but I found no commit evidence for (b)
      in this repo's own history.

Recommendation to lead-opus: re-check where the original "-206,
deterministic, quarantined" claim about raw_sample.arw came from before
relying on it elsewhere in the campaign dossier -- it does not match
current, reproducible, or historical evidence for this file.

Not evidenced either way: whether the INTERMITTENT concurrent-ARW -206
